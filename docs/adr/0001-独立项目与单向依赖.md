# ADR 0001 · 独立项目与单向依赖

- 日期：2026-10-23
- 状态：**已采纳**

## 背景

CPT 与 emotion-core 已经高度耦合（同机、同库、双向数据流 + 单向 HTTP），
但耦合是**约定式**的：表清单写在 markdown 里，列定义两边各手抄一份，
价格常量 emotion 手抄 CPT 的值且**改一边不传播、没有测试会红**。

如果把两个项目合进一个仓，最容易的做法是"搬进去、import 一下" ——
但那会造出**相互纠缠**的依赖网：两个项目的内部实现互相 know，边界消失，
以后任何一边重构都会波及另一边。

## 决策

**Emotion-CPT 是一个独立项目，依赖方向严格单向。**

```
   cpt ─────────┐
                ├──▶ emotion_cpt
emotion_core ───┘

   emotion_cpt ──✗──▶ cpt / emotion_core
```

- Emotion-CPT **不得** import 上游任何模块（`check_contracts.py` 的
  `check_no_upstream_imports()` 强制）
- 上游**可以**依赖 Emotion-CPT 的契约 / 数据层 / 结构层

## 理由

1. **"被治理"不等于"被纠缠"**。单向依赖让共用件可以被强制（改了就红），
   同时不产生双向依赖环。
2. **上游可以逐个采纳**。每一步只改一个 import，失败可单独回滚。
3. **Emotion-CPT 可以独立测试**。契约门禁不需要启动两个上游就能跑。

## 代价

- 上游要接受一个"外部依赖"，发布链路要处理（PyPI 或 Git URL 依赖）
- 契约一旦被 import，就成了对外 API，变更需要版本号 + 弃用期
- ⇒ **在契约被真正 import 之前，先用"校验式"约束**（上游 CI 拉指纹比对），
  这是更现实的第一步
